# Deployment architecture

Terraform composes focused reusable modules for networking, EKS, PostgreSQL,
the External Secrets IAM role, and ECR. The network module creates a two-AZ
VPC with public NAT subnets, private workload/database subnets, and a private
Secrets Manager endpoint. EKS and the managed nodes use private subnets. The
database module creates an encrypted multi-AZ RDS PostgreSQL instance with no
public address in private subnets. It is `publicly_accessible = false` and
accepts TCP/5432 only from the EKS cluster security group. EKS API access is
private-only; deploy it from the VPC-connected GitHub Actions runner.

The database password is generated by Terraform and stored in AWS Secrets
Manager. External Secrets Operator assumes a narrowly scoped IRSA role and
materializes only the database fields needed by the workload as a Kubernetes
Secret. The application uses PostgreSQL TLS (`sslmode=require`) over the
private network. The secret itself is never put in the image or pipeline
output.

Three application replicas use pod anti-concentration, a disruption budget,
rolling updates, resource limits, and startup/readiness/liveness probes. A
PostgreSQL `pg_isready` init container blocks application startup until the
database accepts connections, retrying every five seconds. This handles the
stated 60-second initialization delay (and also works when the database host
is a cluster-local PostgreSQL Service); the application container therefore
does not crash-loop during database recovery. Kubernetes restarts the pod if
the application later exits.

Kyverno is installed by the production workflow at a pinned chart version.
An enforced ClusterPolicy for the `payments` namespace rejects pods that run
as root, enable host namespaces or privileged mode, omit the RuntimeDefault
seccomp profile, permit privilege escalation, use a writable root filesystem,
retain Linux capabilities, omit resource requests or limits, or use a `latest`
image tag. The application deployment uses the commit-SHA image supplied by
the workflow and satisfies these rules.

Kubernetes manifests are organized as a Kustomize base for application
resources, a production overlay for replica count, rolling-update behavior,
disruption budget, namespace, and secret integration settings, and separately
applied Kyverno policies. The cluster-scoped secret store is applied
separately. The workflow renders the production overlay and substitutes only
the secret name and immutable image value; it supplies the AWS region only
when applying the cluster-scoped secret store.

On pull requests, CI validates Terraform, scans infrastructure/manifests and
builds/scans the image. Merges to `main` use OIDC and a protected production
environment to apply Terraform, scan and push a commit-SHA-tagged image, then
deploy it. The production runner must be self-hosted inside the VPC and have
Terraform, AWS CLI, Docker Buildx, Helm, kubectl, envsubst, and Trivy
installed. Bootstrap the encrypted S3 Terraform state bucket and the GitHub
OIDC deploy role before the first run; protect the production environment and
limit that role to the required Terraform, ECR, and EKS operations.

Before provisioning, verify that the selected region supports the configured
EKS and PostgreSQL versions and review the instance sizes, CIDR plan, and
state-bucket policy for the target account.

The modules under `terraform/modules` can be composed independently in other
root configurations. The `payment-platform` module is the example composition
that wires their outputs together. If splitting an already-applied monolithic
state, migrate/import the existing resource addresses before applying the new
module layout to avoid resource replacement.
